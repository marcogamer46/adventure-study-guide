01What you built

Six modules, one pipeline, zero designers: your code builds the world it plays.

Adventure Workbench is a game world — a grid you walk your character through. But nothing in it was hand-made. Your job was to write the code that builds the world and then decides how to move through it. You won't touch any art or engine. All six student modules live in src/student/, and each has one job. The interesting part is how it gets checked: not by a human watching you play, but by an automated referee that runs your code against a fixed specification. By the end of this, you'll be able to explain what each module does, how the pieces connect in a pipeline, and why "same seed, same world" is the backbone the whole thing relies on.

Concept
Module

A single file of code with one clear job. This project has six student modules in src/student/: character.py, artifact.py, enemy.py, terrain_generator.py, level_generator.py, and controller.py.

Deeper
Each keeps the exact function signatures the workbench expects — change them and the referee can't talk to your code.
Concept
Pipeline

The fixed order work flows through: a spec plus a seed go in, the terrain generator builds the map, the level generator places entities, the controller plays the world, and the referee grades the result.

Deeper
Because the order is fixed, each stage knows exactly what shape its input will take.
Concept
Seed and determinism

A seed is a starting number. The same seed always produces the same world — like how the same recipe gives the same cake every time.

Deeper
This is the backbone: because worlds are reproducible, the referee can replay them and compare your behavior against an expected result.
Concept
Snapshot

An immutable picture of the world at one moment — where your agent is, where enemies and patrols are, what you've collected. You can look at it but never change it.

Deeper
Every turn the controller receives a fresh snapshot and must return one action based only on it.
Concept
Action

One choice your controller makes per turn: MOVE, COLLECT, ENGAGE, WAIT, or EXIT.

Deeper
The engine accepts or rejects it, advances the clock, and hands back the next snapshot.
Concept
Referee (validator)

An automated grader. It runs your modules against a spec's private test worlds and reports pass/fail — no human watches your screen.

Deeper
It also drives the real engine (run_public) to replay whole worlds and confirm your character actually reaches the exit.

What you actually built

Adventure Workbench is a game you never see. There's no art, no story, no hand-made dungeon. Instead, there's a world made purely of data — a grid of tiles, your agent's position, enemies, patrols, artifacts, and an exit. You wrote the code that generates that world and then decides how to move through it. If it all works, the whole thing runs end-to-end with no human touching it.

How the pipeline runs

  1. A spec (the rules for this scenario) and a seed (a starting number) go in.
  2. terrain_generator.py carves traversable terrain from that seed.
  3. level_generator.py places the exit, artifacts, enemies, and patrols in legal spots.
  4. Together those two form the World — one reproducible stage.
  5. The controller (controller.py) reads a snapshot every turn and returns one action.
  6. The referee runs validators, then replays the world with the real engine to grade it.
≈
Analogy

The pipeline is a factory assembly line. The terrain generator hands a part to the level generator, which snaps the finished world onto the belt. Then the controller is the worker at the end who reads the label on each item and does exactly one thing to it before it moves on. If any worker stops or does the wrong step, the whole line stalls.

!
Why determinism is the backbone

If a seed produced a different world each run, grading would break: the referee couldn't replay the same test twice, and a lucky or unlucky layout would decide your score. Because the same seed always yields the same world, every run is a fair, repeatable test. That is also why the generators must never lean on randomness that ignores the seed.

What your modules actually do

character.py is deliberately minimal — it builds your agent's identity and fails fast if the id is invalid. The heavy lifting is in controller.py. It doesn't wander: it plans a lowest-cost path to the exit using Dijkstra's algorithm, a standard search method, tracking position, turn, and which enemies are defeated. It predicts where patrols will be before moving, so it never collides with one. It collects artifacts on the tile it stands on, engages static enemies that block the route, and exits the moment it reaches the exit tile.

Real numbers from the project

The verification log records what actually passed: all 18 distinct spec groups pass both referee sessions. The controller completes all 142 certified engine worlds across every topology and mode — including all 8 patrol worlds. And a full live run of the real engine completes 8 of 8 straight-path worlds with a perfect score of 100.

✕
The #1 wrong idea

It's easy to picture a robot watching a little character shuffle around a screen and nodding. That's not how this works. The referee is a program, not a spectator. It runs your modules against hidden test worlds, checks their outputs against the spec, and replays full worlds through the real engine to confirm your agent actually reaches the exit. No human watches your screen — the grading is completely programmatic.

!
The real point: defending code

This whole project is practice for a harder skill: standing behind code you didn't fully write yourself. AI drafted much of this. Your job isn't just to make it run — it's to understand each module well enough to explain it, defend its choices, and spot where it could go wrong. That's why each module is small and each idea maps to one clear concept: procedural generation, pathfinding, decision loops, and testing against a spec.

02The world model

Your world is just a grid of floor and wall cells. Read it right and nothing sneaks past you.

The world is the stage every other rule stands on. Before you can judge how an AI-written character moves, collects, or fights, you have to understand the ground under its feet. In this project the world is not a physics engine — it is data: a rectangle cut into small squares, each holding one of two symbols. By the end you can read any world from its raw text, tell a walkable cell from a wall, translate a position into a row and column, and know what a snapshot of the world contains. That is the foundation for defending everything else.

Concept
Cell

One square of the grid, holding a single character. It is either floor ('.') or wall ('#').

Deeper
Cells are the smallest unit; an agent moves between neighboring cells one step at a time, north, south, west, or east.
Concept
Terrain

The whole layout of the world: a rectangular list of text rows, each row a string of '.' and '#' characters.

Deeper
Terrain is stored as a tuple of strings, so the world is literally text you can open and verify.
Concept
Position

One specific cell's address, written as Position(row, column). Row 0 is the top row, column 0 is the left column.

Deeper
Order matters: row comes first. Confusing it with (x, y) flips your entire map.
Concept
Traversable

The single question the terrain answers: can a character stand on this cell? Only floor cells are traversable, and only when the position is inside the grid.

Deeper
A wall is not a physical obstacle — it is simply a cell where is_traversable returns False.
Concept
WorldSnapshot

A frozen copy of the world at one moment in the game: the terrain, where the agent is, the current turn, what's been collected, and which actions are allowed.

Deeper
It is immutable — you can read it but not change it. Each turn hands you a fresh snapshot.
Concept
Start and exit

Two distinct marked cells: where the agent begins, and where it must arrive to finish.

Deeper
They must be different cells, and the floor between them must stay connected or the level cannot be won.

What the world is

The world is a rectangle cut into small squares called cells. Each cell holds exactly one character of text. A '.' means floor — you can stand there. A '#' means wall — you cannot. In the code, the whole world is just a list of text rows, one string per row. Here is a tiny world, 2 rows tall and 3 columns wide: .## ... Row 0 is '.##': a floor, then two walls. Row 1 is '...': three floor cells. That is the entire world. Nothing hidden behind it.

≈
Analogy

Picture a street map drawn on graph paper. Each square is one city block. A floor cell is an open plaza — you can stand on it. A wall cell is a building — you cannot walk through it. The whole map is just labeled squares; the buildings don't have physics. They are simply squares you are not allowed to stand in.

How to read a position

  1. A position is written Position(row, column).
  2. row is how many rows down from the top — row 0 is the very top.
  3. column is how many columns right from the left — column 0 is the far left.
  4. So Position(1, 2) means: down one row, over two columns.
  5. To ask whether you can stand on a cell, call terrain.is_traversable(Position(row, column)).

Terrain answers one question

Terrain answers exactly one question: is this cell walkable? The answer is yes only when two things are both true: the position is inside the grid, and the cell's character is '.'. That is the whole job. A wall is not an obstacle in some physical sense — it is just a cell where is_traversable returns False. There is no climbing, no breaking walls, no diagonal shortcuts. You step north, south, west, or east into a floor cell, or you stop.

✕
The #1 misconception: position order

Misconception: a position is (x, y), like a graph. In this code it is not. Position takes row first, then column — and row 0 is the top, not the bottom. If you mentally swap them, every move is mirrored: up becomes right, down becomes left. When you read an AI-written project, getting this backwards turns a correct solution into an invisible bug.

The invisible rules

The world also follows strict rules, and these are where broken AI-generated levels get caught. Every row must be the same length — otherwise the rectangle is not a rectangle. Every character must be '.' or '#'. And every floor cell must connect to the others in one unbroken region — no floating islands of floor cut off by walls. If a floor tile is unreachable, the level cannot be finished. The validator checks all of this, and so can you.

Start, exit, and the snapshot

A level marks two special cells: start, where you begin, and exit, where you must arrive. They are always distinct cells. And at each moment of play you get a WorldSnapshot — a fixed, readable copy of the world at that turn. It bundles the terrain, the agent's current position, the turn number, what has been collected and defeated, and which actions are allowed right now. It is frozen: you can look at it, but nothing you do changes this particular copy. Every turn hands you a fresh one.

!
Why defend the world

Why learn to read a world? Because in this project the world is data, not magic. It is text you can open and check. Look for a row with the wrong length, a stray character, a disconnected island of floor, or a start and exit that cannot connect. Catch one of those and you have found a real defect — and you have defended the project against an AI that almost made it look fine.

03The entities

Three small objects hold the whole game world — and every one checks its inputs before it exists.

This lesson covers the three building blocks that describe everything in the game: the player character, the artifacts you collect, and the enemies that punish you. Each one is a small Python class — a blueprint for making objects. By the end you will understand what an entity is, where its data comes from, and why creating one is more than just storing a few numbers. You will see why a negative score gets rejected instead of quietly fixed, and why every value is read-only once it exists. That pattern is the first line of defense in this AI-written codebase: garbage gets stopped at the door, never silently accepted.

Concept
Entity

An entity is any object in the game world that has a fixed identity — here, exactly three kinds: the character, artifacts, and enemies.

Deeper
Each entity wraps a canonical definition from src.api, so the game never carries two slightly different copies of the same fact.
Concept
Canonical definition

A canonical definition is a single, authoritative description of what valid data looks like, defined once in src.api and reused by the whole project.

Deeper
Because all validation lives there, every place that creates a character, artifact, or enemy gets the same rules automatically — no one can bypass them.
Concept
Read-only property

A read-only property is a value you can look at but never change after the object is created.

Deeper
The @property decorator with no setter means nothing outside the class can reassign it — the data is frozen, which prevents accidental edits.
Concept
Fail-fast validation

Fail-fast validation means rejecting bad input the moment it arrives, rather than fixing it or ignoring it.

Deeper
A negative artifact value or empty ID raises an error immediately at creation, so a bug becomes loud and obvious instead of hiding until later.

What an entity is

Think of the game world as a stage. The stage itself is the terrain. The things that live or move on it are the entities. In this project there are exactly three kinds: the character (you), artifacts (things worth points), and enemies (things that cost you points if you run into them). None of them are complex — together they are only three small classes — but how they are built matters more than what they contain.

How one entity is built

  1. You call the class with its data, for example Artifact("relic", position, 50).
  2. Before doing anything else, it builds the canonical ArtifactDefinition from src.api, handing over your inputs.
  3. That definition validates everything: the id must be a nonempty, already-trimmed string; the position must be a real Position (two integers); the value must be an integer that is zero or positive.
  4. If any check fails, the class raises an error right there — the object is never created, and nothing is stored.
  5. Only if everything passes does the object save the values and expose them as read-only properties: artifact_id, position, and value.
≈
Analogy

Imagine a toll booth at the entrance to a game. You hand over your ticket and your money. The attendant checks both: the ticket must be real and nonempty, the money must be a genuine number and not negative. If you hand over a ticket that is blank, or money that is -5, you are turned away at the door — you do not get in with a quietly "fixed" ticket. That is exactly what these classes do. They are strict border guards, not helpful friends who smooth over your mistakes.

The three entities at a glance

  • Character(agent_id) — holds only your player id, an identifier string. Exposes agent_id.
  • Artifact(artifact_id, position, value) — holds an id, a spot on the grid, and a point value that must be zero or positive. Exposes artifact_id, position, value.
  • Enemy(enemy_id, position, encounter_penalty) — holds an id, a spot, and a penalty that likewise must be zero or positive. Exposes enemy_id, position, encounter_penalty.
  • Note: enemies have no health and no attack. They are not fighters here — they are just a cost you pay for stepping on the wrong tile.

Why 'canonical' matters

Each student class is deliberately thin. It does almost no thinking itself — it delegates to a shared definition in src.api. That is the point. If the game ever grows and needs a new rule (say, ids must be under twenty characters), you change it in one place, and every entity that uses it picks up the rule automatically. One source of truth beats three slightly different copies of the same idea. This is a classic defensive design: fewer places for rules to drift apart.

✕
Misconception: bad input should be fixed, not rejected

A natural instinct is: if someone passes a negative artifact value, just clamp it to 0 and move on. This project deliberately does the opposite. Silently clamping hides the bug — the code keeps running, but with data that does not match what the caller meant. Rejecting it loudly makes the mistake visible the instant it happens, while the cause is still right in front of you. In a codebase you have to defend, loud and early beats quiet and wrong.

!
The defensive takeaway

The entities are the whole world's data, and every one of them is immutable — read-only after creation — and validated at the front door. That combination means two things for you as a defender: bad data cannot sneak into the game, and once data is in, nothing can quietly change it later. If you are ever asked why the code feels rigid, this is the reason: rigidity here is a feature, not a bug.

04Terrain generation

One number and one shape rule in; the same floor-and-wall map out, every single time.

Every level in this project has a map: a grid of floor tiles you can walk on and wall tiles you can't. Somebody builds that map, and that somebody is a small piece of code called the terrain generator. You'll learn that what looks like "random terrain" isn't really random — it's driven by a number called a seed, so the exact same map can be made again and again. By the end you'll be able to explain the four map shapes the generator can make, say what "connected" means and why every map guarantees it, and answer a reviewer who asks how one run could ever match another.

Concept
Seed

A number you give the generator; it decides which terrain comes out.

Deeper
Same seed always yields the same map, even across two completely separate runs of the program.
Concept
Pseudorandom generator

A machine that makes numbers that seem random but are actually strung together from the seed, so they're repeatable.

Deeper
random.Random(seed) is built fresh inside the method on every call, so nothing random is remembered between calls.
Concept
Topology

The shape rule for a level — the pattern the floor must follow.

Deeper
Chosen from four presets; swapping it changes the whole feel of a level.
Concept
Connected

All floor tiles link up, so you can walk from any one to any other without touching a wall.

Deeper
Even the loosest topology guarantees this — there's never a floating island of floor.
Concept
Tree and branch

A shape with no loops — every floor tile reaches the rest of the map in exactly one way, so there's a single path to follow.

Deeper
A branch is a tile with three or more floor neighbors; branching trees must contain at least one.
Concept
Deterministic

Same inputs always give the same output. No surprises.

Deeper
That's what lets a level be replayed and scored fairly.

The stage: a grid of floor and wall

The world is a rectangle divided into cells. Each cell is one of two things: floor, written as ".", or wall, written as "#". Floor is where the player walks; wall stops them. A terrain is just the full set of rows, each row a string of dots and hashes. Generating terrain means deciding, for every cell, whether it becomes floor or wall.

How a terrain is generated

  1. Read the spec: how many rows and columns, the allowed range of floor tiles, and the shape rule (topology).
  2. Make the random generator from the seed: rng = random.Random(seed). This is the only place the seed is used, and it is rebuilt on every call.
  3. Pick how many floor tiles to carve — the target — choosing within the allowed min/max range using that generator.
  4. Hand the shape rule the generator, the grid size, and the target. It chooses which cells become floor.
  5. Paint the grid: start with all walls, mark the chosen cells as floor, and return the finished rows.
≈
Analogy

A seed works like agreeing on the exact order a deck is shuffled. In real life, ten people can't shuffle "the same way" — but here they can. Give the generator the seed 42, and it always deals the same terrain. Change it to 43, and you get a different but still repeatable map. The randomness is fake on purpose: it's a fixed recipe, and the seed is the one ingredient you may change.

The four shapes (topologies)

  • STRAIGHT_PATH: a single corridor of floor running along one axis — horizontally if the board is wide enough, otherwise vertically. One line.
  • BENT_PATH: an L-shape. A horizontal arm meets a vertical arm at a corner, and the total floor cells equal the target.
  • BRANCHING_TREE: a shape with no loops, like a family tree drawn on the grid; it must contain at least one cell where three or more arms meet (a branch). It's built by adding cells that touch exactly one existing floor neighbor, so no loop can form.
  • GENERAL: any connected shape. The only rule is everything links up.
!
Why determinism is the whole point

Because rng is built fresh from the seed inside the method, two brand-new generators with the same seed and spec cannot disagree. That's what makes a level fair to grade and safe to replay: you, or a referee, can recompute the exact same map later. If the generator had kept hidden random state on itself instead, a second run might quietly differ — a nasty class of bug the AI writer avoided by keeping state local.

✕
The #1 misconception

"It uses random, so nobody can reproduce the map." Wrong. The "random" is seeded, so it's fully repeatable. Randomness here doesn't mean unpredictable — it means varied-but-identical-for-the-same-seed. If a reviewer says this can't be tested because it's random, that's the exact misunderstanding to correct.

!
Branching trees get retried

Branching trees rarely come out right on the first try. The generator grows a candidate tree once, checks whether it hit the target floor count and has a branch, and if not, throws it away and grows a fresh one — using the same seeded generator each time, so even the retries are reproducible. The number of tries is capped, so it can't loop forever.

Reading the output

End to end, you get back a Terrain object whose rows are strings of '.' and '#'. That's the whole contract. Given the same seed and spec, those strings will be character-for-character identical every time. That's the guarantee you can point at when someone asks why a level can be rerun.

05Level generation

Your map doesn't draw itself — and knowing who draws it is half the defense.

A video game level is a little world: some walkable floor, a place you start, a place you leave, and things you grab or avoid. Building that by hand is fine for one map, but this project creates many levels from a small description. That job belongs to a piece of code called LevelGenerator. By the end of this section you can explain how it works: how it gets the terrain, how it chooses where you start and exit, and how it decides where artifacts and enemies sit. You will also see the invisible rules that keep every generated level fair and legal.

Concept
Contract (TerrainGeneratorContract)

A promise between two pieces of code: anything that supplies me terrain must answer these calls, and LevelGenerator expects exactly that without caring who the builder is.

Deeper
Because LevelGenerator never makes terrain itself, swapping one builder for another changes the map style without touching the rest of the code.
Concept
Degree-one cell

An open, walkable tile that touches only one other open tile — in other words, a dead end or the tip of a corridor.

Deeper
For straight and bent corridors, a path has exactly two such tips, so those become the start and exit.
Concept
Manhattan distance

The number of steps from one tile to another if you can only move up, down, left, or right — no diagonal shortcuts.

Deeper
It is the route length on a grid, and the code uses it so start and exit are neither too close nor too far apart.
Concept
Seeded random number generator

A random number machine you can rewind: give it the same seed (a starting number) and it produces the exact same sequence of random choices every time.

Deeper
That is why the same seed always rebuilds the identical level — the key to reproducing and testing a bug.
Concept
Traversable tile

A floor tile you can stand on, as opposed to a wall tile you cannot.

Deeper
Entities are never placed on walls, because they could not be reached.
Concept
Endpoints

The start and exit tiles of a level.

Deeper
Different map shapes pick these differently, which is the part worth watching.

What level generation really is

Building a level is assembly, not invention. LevelGenerator takes a specification (a written description of what the level should contain) and a seed, then runs three phases: get the terrain, choose start and exit, and sprinkle in the artifacts and enemies. Each phase follows fixed rules, and those rules are the whole point of this reading: a reviewer will ask you why a level looks the way it does, and the answer lives in these rules.

The terrain is borrowed, not built

First, the terrain. LevelGenerator does not draw the map. It is given a terrain generator at startup through a thing called a contract — a promise that whatever generator is handed over can produce terrain, This is called dependency injection: the code that needs a service receives it from outside instead of building it itself. So the layout comes from somewhere else, and LevelGenerator just asks for it.

The pipeline, step by step

  1. Trust the terrain: call the injected generator to build the map, returning walkable ('open') and blocked tiles.
  2. Collect open tiles: scan every tile and keep the ones you can stand on.
  3. Pick endpoints: choose start and exit using the shape of the terrain.
  4. Place entities: drop artifacts and enemies onto open tiles under the fairness rules.
  5. Ship the level: bundle seed, terrain, start, exit, artifacts, and enemies into a finished LevelDefinition.

How start and exit get chosen

How endpoints get picked depends on the map's shape. For straight or bent corridors, a path has exactly two dead ends — tiles with only one neighbor, called degree-one cells. Those become start and exit. For trees and general open maps, the start is simply the top-left open tile, and the exit is the first other tile whose Manhattan distance (step count) falls inside the requested minimum and maximum route moves. If nothing qualifies, it falls back to the last open tile. Every case bounds the route length, which keeps the level playable instead of absurdly short or long.

≈
Analogy

Think of a restaurant that cannot cook. It does not grow its own food; it orders from a supplier who promises delivery. The supplier may change, but the restaurant's orders stay the same. LevelGenerator is the restaurant. The terrain generator is the supplier. The contract is the delivery promise — as long as the supplier honors it, LevelGenerator never needs to know how the food (or the map) was made.

✕
The #1 wrong idea

The biggest misconception: 'The level generator designs the whole map itself.' It does not. It borrows the terrain from an injected builder. Its own work is picking endpoints and placing entities. Confusing those two jobs leads you to look for layout logic in the wrong file — and to miss the boundary where bugs and exploits tend to hide.

Where entities may go

  • Entities only go on open, walkable tiles — never on walls.
  • Enemies are never placed on the start tile; that would be unfair.
  • Unless allowed, both artifacts and enemies also avoid the exit tile.
  • Unless overlapping is allowed, no two entities share a tile.
  • Each entity gets a unique id — ART-1, ENM-2 — so the game can tell them apart.
  • Artifact values and enemy penalties are rolled from the specification's range using the seeded random numbers, so they vary but stay within bounds.
!
Why these rules matter

These rules are guards, not decoration. They guarantee a level is always beatable and fair no matter what the random numbers say. When you defend an AI-written project, this is the exact spot to check: did the writer put limits on randomness? Can an enemy land on the start, or an artifact on the wall? These invariants are the backbone of a trustworthy generator.

06The controller

The controller is the robot's brain: each turn it reads the world and picks exactly one move.

Every turn of the game, the world changes around the agent, and someone has to decide what it does next. That someone is the controller: a block of code that runs once per turn, looks at the current state (where the agent is, what it has, where the enemies are), and returns exactly one action. By the end of this section you'll be able to explain the controller's decision order in your own words, say why standing on something is never enough on its own, and answer a reviewer who asks why the controller behaves the way it does.

Concept
Action

One thing the agent can do on its turn: move north, south, west, or east, collect an artifact, engage an enemy, wait, or exit.

Deeper
The controller MUST return exactly one action every turn, even if the right choice is to do nothing (that's the WAIT action).
Concept
Turn

A single step of the game, where the controller reads the world and answers with one action.

Deeper
Every accepted action advances the patrol clock by one turn, so the world shifts even when the agent stands still.
Concept
Patrol

What the controller is

The controller is the decision-maker. It does not move the agent itself; it only chooses. Each call to choose_action(state, agent_id) reads the current world and returns one action. The game then applies that action and advances to the next turn. Nothing else decides for the agent, this one function is the whole brain.

The decision order

  1. If the agent is standing on the exit tile, return EXIT.
  2. Else, if an uncollected artifact is on the agent's own tile and no patrol will arrive there next turn, return COLLECT.
  3. Else, follow the plan: return the first step of the lowest-cost path toward the exit.
  4. If there is no usable plan, return WAIT.
≈
Analogy

Think of the controller as a taxi driver at an intersection. The driver doesn't decide the whole ride upfront every second; they look at what's ahead right now and make one call, turn left, wait, merge. When the light changes, they re-look. The controller works the same way: every turn it looks fresh and picks the single best next move, so it can react to patrols moving and meters getting collected.

!
Arriving is not leaving

This is the sharpest edge in the whole file. Walking onto the exit tile does not end the level. The code checks, if position == state.level.exit, return EXIT. Reaching the tile is only half; the controller must actively return the EXIT action to win. The same idea applies to artifacts: standing on one never collects it, the controller has to choose COLLECT.

✕
The biggest wrong idea

Many people assume that stepping onto an exit or an artifact automatically triggers it, like a checkpoint in a platformer. It does not. In this project, moving onto a tile and acting on it are separate decisions, and the controller must explicitly commit the EXIT or COLLECT action. If you review the code and see the agent standing on the exit but the loop not ending, that is almost always the controller returning the wrong action instead of EXIT.

Why the checks are ordered

Order matters. The exit check runs first, so the agent always leaves the moment it can. The collect check runs second and is guarded: it only collects if no patrol is about to arrive on that tile, because collecting costs one turn and a patrol landing on you is a collision. Only after those quick checks does the controller fall back to the slow pathfinding plan, and if even that has no route, it waits rather than guess.

07How the controller plans

It doesn't guess. It maps every route, prices them, and walks the cheapest one.

A controller that just "heads toward the exit" is a dead end. In one map I looked at, the first step away from the exit is a wall, so that controller has no legal move - and when it's allowed to do nothing, it just waits forever. That's a bug you want to catch. The real planner thinks ahead. It searches over every reachable state, prices each route by how many actions it costs, and picks the cheapest one. By the end of this section you'll be able to explain that search, why the turn number is part of each state, and why a longer detour can beat a straight path.

Concept
State

A snapshot of where you are: your position on the grid, the current turn, and which enemies are already defeated. Two states are different if any of those three things differ.

Deeper
This is the trickiest part: the same tile at turn 5 and turn 12 is a different state, because the floor plans move with the clock.
Concept
Cost

How expensive a route is in actions. A normal move or WAIT costs 1; engaging an enemy costs 1 plus its encounter penalty.

Deeper
The planner compares these numbers, not the number of tiles. A detour of 6 actions beats a straight path through an enemy that costs 13.
Concept
Dijkstra's algorithm

A way to explore routes in order of cost, cheapest first. Because it always explores the cheapest known route next, the first time it reaches a state, that route is the cheapest way to get there.

Deeper
It uses a priority queue (a heap) so it can grab the cheapest not-yet-explored route each loop. As soon as it reaches the exit, it stops and walks the path backward.
Concept
Patrol clock

Patrols move once per accepted action, so their future position depends on how many turns have passed. Planning against their future spots - not just where they are now - is why the turn is in the state.

Concept
Encounter penalty

An extra cost charged for fighting a static enemy, set per enemy in the level. It's what makes the planner weigh fighting vs. going around.

Deeper
Patrols can't be fought at all - they're only timed around. Only static, undefeated enemies are clearable blockers.
Concept
The WAIT-lock bug

What happens to a naive controller with no legal move: since waiting is allowed, it just waits forever instead of recovering. The planner avoids this by always having a whole route computed before moving.

Deeper
If the planner can't reach the exit at all, it returns no plan and the controller falls back to waiting - but that's a last resort, not its normal behavior.

Where a dumb controller dies

Start with the version you'd write in five minutes: always move one step toward the exit. It works until the step right next to the exit is a wall. Now it has no legal move - and since WAIT is allowed, it just stands there forever. That's the WAIT-lock bug. It's not a clever failure; it's a controller that never looked more than one step ahead.

≈
Analogy

Picture the map as a road network. Each tile is an intersection, each corridor is a road, and every road has a toll. Moving costs 1, and walking into a battle is an expensive toll booth. Pit plans the whole trip ahead of time: load all the routes it can reach, add up the tolls, and commit to the cheapest one. A detour that costs 6 beats a 'straight' road that runs through a 13-toll battle, every time.

How the search works

  1. Start with one state: your current position, your current turn, and the set of enemies already defeated.
  2. Repeatedly pop the cheapest not-yet-explored state off a priority queue (a heap).
  3. From it, consider every move: north/south/east/west (cost 1), ENGAGE an adjacent static enemy (cost 1 plus that enemy's penalty), or WAIT (cost 1).
  4. Each move produces a new state - position changed, turn bumped by one, enemies defeated grown - and you record the cheapest cost found to reach it.
  5. Because you always explore cheapest first, the first time you reach the exit tile, the route you found is the cheapest one. Stop there.
  6. Walk the recorded 'previous' pointers backward from the exit to the start, then reverse them to get the ordered list of actions.
!
Why the turn is part of a state

Patrols move with the clock: their position is computed from the schedule, the turn, and their start phase. The same tile at a different turn is a different state, so the planner must consider where patrols will be in the future, not just now. A route is only legal if the next tile is clear now and stays clear right after the move advances the clock - the code checks both the current and the next-turn patrol positions.

!
Fighting is priced, not free

Engaging a static enemy costs one action plus its encounter penalty. That penalty is the whole point: it makes the planner decide between clearing a blocker or going around it. Patrols are never engaged - only timed around. So the route you get reflects a real trade-off, not a fixed path.

✕
Misconception: shortest means fewest tiles

The common wrong idea is that the planner minimizes the number of tiles traveled. It doesn't. It minimizes total cost: actions plus encounter penalties. That's why a detour of 6 actions is chosen over a path through an enemy that costs 13. If you read this code and think it's 'just pathfinding,' you'll miss the whole reason the cost function exists.

When the exit is unreachable

If no route to the exit exists, the search ends with no goal and returns no plan. The controller then falls back to WAIT - which is where the WAIT-lock bug lives, but now as a deliberate last resort rather than an accident. It's the difference between a controller that has no option and one that has no plan.

08Enemies & patrols

You can't fight a patrol. You read its route, time your move, and thread through.

This world has two kinds of enemy, and they punish you differently. A static enemy sits on one cell and never moves. You clear it by paying a toll. A patrol walks a fixed route in a loop, forever. You can't fight it, you can only predict where it'll be and slip past. By the end of this lesson you'll know exactly how patrols move, what ENGAGE actually does, and the one rule that decides whether you survive a crossing.

Concept
Static enemy

A blocker that stands on one cell and never moves. You clear it with ENGAGE while standing on a neighboring cell.

static Blockers

Cleared with ENGAGE

A static enemy sits still on one tile. If it's adjacent, you can ENGAGE it: it disappears, you pay its penalty, and you don't move. Next turn you step into the cleared tile. Once defeated, it's in defeated_enemy_ids and won't be re-engaged.

patrol Moving guards

Cannot be engaged

A patrol follows a repeating schedule of positions (positions plus an initial_phase). It advances once per accepted action — including yours. You may not ENGAGE it. The only winning move is timing: move into cells it isn't about to occupy.

The collision rule

After you take an accepted action, patrols advance. If your destination cell is occupied by a patrol at that next moment, you collide and lose. So a safe move must be clear now and clear right after the clock advances.

Why "once per accepted action" matters

Rejected moves don't advance the clock — but WAIT, COLLECT, and ENGAGE all count as accepted actions and do. That's why a controller can't just "wait forever" in a patrol world: waiting moves the guards.

!
No combat, no killing

ENGAGE is not a fight mechanic. Enemies have no health, no attacks. ENGAGE is simply clearing a blocker and paying its penalty. A reviewer will press you on this — be able to say it plainly.

09Scoring & limits

Your score isn't about finishing — it's about how close you stayed to the cheapest honest route.

When you run an adventure level, the game turns your choices into a single number: your score. This section shows you exactly how that number is computed, and why the details matter when you have to defend an AI-written project. By the end, you'll be able to compute a score by hand from a run's events, explain what the reference cost means, and see why "just finish" is the wrong strategy. You'll also meet the two hard limits, H and D, that keep a run finite. Everything here is read from the real code, not invented.

Concept
Action (turn)

One decision you make for the explorer — moving to a neighboring tile, waiting, or taking the exit. The code counts every accepted action and calls that number T.

Deeper
The exit move itself counts as a turn, so T is not just walking moves.
Concept
Encounter penalty (P)

If you step onto a tile holding an enemy, the game charges you a fixed penalty — a number added to your cost. P is the sum of every penalty you paid.

Deeper
Penalties are set when the level is built; larger enemies cost more points.
Concept
Total cost (C)

Your total cost is your turns plus your penalties: C = T + P. It measures how expensive your chosen route was, in effort plus damage.

Concept
Reference cost (L)

The reference cost is the cheapest honest route through the level, computed for you before the run. It is the baseline that 'good' is measured against.

Deeper
You earn points by staying near L — not by moving fast, and not by collecting the most.
Concept
Excess (E)

Excess is how far above the reference cost you went: E = max(0, C - L). The max(0, ...) means going under L is not 'negative excess' — it triggers a separate flag.

Deeper
This is the single number that actually moves your score down.
Concept
Base points, deduction rate, threshold (B, r, Q)

Deeper
B, r, and Q come from the tuning() function, which sizes them to the level's size: big levels get bigger B and Q, so a 'good' run is equally hard everywhere.

What a score really measures

Every run ends with a number: the score. In this family, the score is not 'how much you collected' and not 'how fast you were.' It is a measure of how close your route came to the cheapest honest route through the level. Grasping that distinction is the whole game — and it is exactly what a reviewer will probe when they look at an AI-written project. If you can reproduce the calculation yourself, you can tell whether a score is fair or whether something in the code is quietly wrong.

The calculation, step by step

  1. Count every accepted action — each move, wait, and the final exit — and call that T.
  2. Add every enemy penalty you paid, and call that P.
  3. Add them: C = T + P. That is your total cost.
  4. Compare C to the reference cost L. Excess is E = max(0, C - L).
  5. Start at base points B, add any artifact rewards A, then subtract r points for each unit of excess. That gives your score.
  6. Force the score to zero if any of these are true: the run never completed, excess reached Q, or you finished under the reference cost (a defect).
!
The real numbers

These are not hypothetical. From the actual code, the simple straight passage (tier 0) ships with B = 100, r = 5, Q = 14, and a 32-turn cap H. The big combined world (tier 7) has B = 975, Q = 230, H = 512. Because tuning() grows B and Q with the level's size, a 'good' run costs about the same effort on every level. A run with C = 13 and L = 5 has E = 8 and scores 100 - 5*8 = 60; a run with C = 6 has E = 1 and scores 95.

≈
Analogy

Think of the level as a toll highway. The reference cost L is the price of the cheapest honest route from entrance to exit, and you start with B dollars in your pocket. Every tile you walk costs $1, and stepping on an enemy adds its penalty. The moment your total bill passes L, every extra dollar is taken straight out of your B dollars, r at a time. Run the bill high enough — up to Q — and you are cleaned out: a flat zero.

Two things that trip people up

First, artifacts are worth points: your reward A is added to the base before deductions, so grabbing a valuable artifact can legitimately cover extra wandering. Second, finishing faster than the reference cost is not a win. The code flags a completed run whose cost is below L as a defect and scores it zero. That is an anti-cheat guard: a real run should not beat the certified cheapest route, so a suspiciously fast finish is treated as invalid.

✕
The #1 misconception

'Finishing is what matters — take your time and grab everything.' Wrong. You are scored on staying near the reference route, not on reaching the exit. Padding your walk with extra turns pushes excess up, and once excess reaches Q the entire score collapses to zero. More time is not more credit; it is slowly spending down your base points.

The limits: H and D

Two hard stopwatch limits keep runs finite. H is the maximum number of turns you are allowed: hit it without exiting and the run is simply over, incomplete, and scores zero. D is the patrol deadline, used only in the tier-8 patrol worlds, where the patrol schedule is certified against this bound. Both exist so a player cannot stall forever to dodge enemies or wander indefinitely — and so a reviewer can rely on every run being bounded.

10Why seeds matter

Same seed, same map — every time, on every machine, for every player. That's determinism.

Every map here comes from just two inputs: a specification (the rules — how big, how many open tiles, what shape) and a seed (one integer). This section is about why that seed matters so much. By the end you'll be able to explain why the same seed must produce the identical map on every fresh run, how the referee verifies it, and why the tempting shortcut of remembering the last map quietly breaks the whole system.

Concept
Seed

A seed is a single number (never negative) that acts as the starting point for every 'random' choice in the generator. Same seed plus same rules equals the same map.

Deeper
In the code, random.Random(seed) builds a private random-number machine from it, and every coin flip the generator makes pulls from that one machine in a fixed order.
Concept
Determinism

Determinism means identical input always produces identical output — here, the same spec and seed must produce the exact same grid of tiles.

Deeper
It must hold across fresh instances, not just within one object: a brand-new generator with the same spec and seed must draw the same map.
Concept
Canonical record

A canonical record is a frozen, standardized snapshot of a request or its output, written in one exact format so it can be compared byte for byte.

Deeper
The referee encodes a map's geometry as canonical bytes and fingerprints them with a SHA-256 digest, so 'did these two runs match?' becomes a simple byte comparison.
Concept
Referee

The referee is the automated judge that runs your generator, checks its output against the rules, and decides pass or fail.

Deeper
To test determinism it runs an A/A/B/A sequence on one object, then repeats request A on a separate fresh instance and insists every copy matches.

A map from a thousand coin flips

This project builds a map — a grid of open floor tiles ('.') and walls ('#'). There is no artist drawing it. Instead the generator makes a long string of choices: which row to start on, how long a hallway should be, where to branch. Left alone, those choices would be different every run. That is the problem a seed solves.

How a seed pins it down

Look at the very first step of the generator's work: rng = random.Random(seed) (src/student/terrain_generator.py, line 86). That creates a private random-number generator seeded from your integer. Every random call the generator makes — picking a row, a column, a corridor length, a branch point — pulls from this one rng, in a fixed order. Same seed means the same sequence of numbers in the same order, so the map is fully decided by the spec plus the seed, and nothing else. If you didn't create this local RNG and instead fell back on the program-wide random module, the seed would do nothing and every run would drift.

What the referee actually demands

  1. It freezes your request — that spec and seed become a canonical record — before anything runs. From here, ground truth is bytes, not vibes.
  2. It builds one generator object and asks for request A, then A again, then a different request B, then A a third time. All three A answers must be byte-identical.
  3. It builds a second, brand-new generator and asks for request A once more. That answer must match too. This is the fresh-instance test.
  4. If the fresh instance disagrees, it flags NONDETERMINISM with code CONTENT_MISMATCH. If the factory hands back the same object instead of a new one, it flags SHARED_INSTANCE. Both are failures.
≈
Analogy

You've probably seen this before: in games like Minecraft, a world seed is a short string, and that seed generates the same landscape for every player, every time. This is the same idea. The spec is the shape of the canvas; the seed is which of the infinite possible maps gets painted on it. Anyone with the same spec and the same seed must see the identical map — including a brand-new copy of the generator. That shared, repeatable map is what lets the referee check your work fairly.

!
Even the retries are on the seed's stream

An easy place to break determinism is the retry loop. For the branching-tree topology, the generator tries to grow a tree up to max(max_attempts * 4, 8) times. Each failed attempt calls _grow_tree again — but every attempt draws from the SAME seeded rng, so it consumes the next numbers in the same fixed stream. The retries are part of the deterministic sequence. Any code that 'tries again' must keep pulling from the seeded RNG, never from fresh global randomness, or the replay diverges.

✕
Myth: remembering the last map is a harmless shortcut

The classic trap: cache the last generated map on the instance and return it when the same spec and seed come in again. It looks like a speedup and it passes the within-one-object check. It fails the moment the referee builds a SECOND instance: a fresh object has no cache, so it regenerates from scratch — and whether that regenerate matches depends on randomness the seed didn't control. Determinism isn't 'this object remembers'; it's 'any fresh object, given the same spec and seed, independently arrives at the same map.' The fix is almost backwards: don't store results on the instance at all. Recreate the local random.Random(seed) and recompute every time.

Why you should care beyond the grade

Determinism isn't teaching-assistant trivia. Because the map is a pure function of spec and seed, a bug is reproducible: hand a teammate the exact spec and seed and they watch the same broken map appear. And when the referee re-runs your submission against a canonical record, it can prove the output is genuine and repeatable — that's the difference between 'a map was made' and 'this specific map, made from this specific seed.'

Analogy

Think of static enemies as doors and patrols as moving guards. You do not kill either one. """TODO: generate canonical terrain deterministically from specification and seed."""
import random

from src.api import Terrain, TerrainGenerationSpec, TerrainTopology


class TerrainGenerator:
    """Keep state local; identical inputs must also agree across fresh instances."""

    def __init__(self) -> None:
        self._last_seed = None
        self._last_spec = None
        self._generated = 0

    @staticmethod
    def _neighbors(row, column):
        return ((row - 1, column), (row + 1, column),
                (row, column - 1), (row, column + 1))

    def _straight_path(self, rng, rows, columns, target):
        # A single line of floor on one axis. Prefer horizontal when it fits.
        if columns >= target:
            row = rng.randrange(rows)
            start_column = rng.randrange(0, columns - target + 1)
            return {(row, column) for column in range(start_column, start_column + target)}
        column = rng.randrange(columns)
        start_row = rng.randrange(0, rows - target + 1)
        return {(row, column) for row in range(start_row, start_row + target)}

    def _bent_path(self, rng, rows, columns, target):
        # One L-shape spanning both axes: a horizontal arm plus a vertical arm
        # sharing the corner, with total open cells == target.
        for _ in range(200):
            row = rng.randrange(rows)
            column = rng.randrange(columns)
            # horizontal length h in [2, columns-column], vertical v in [2, rows-row]
            # with h + v - 1 == target.
            v_min, v_max = 2, rows - row
            h_min, h_max = 2, columns - column
            low = max(h_min, target + 1 - v_max)
            high = min(h_max, target + 1 - v_min)
            if low <= high:
                h = rng.randint(low, high)
                v = target + 1 - h
                cells = {(row, c) for c in range(column, column + h)}
                cells |= {(r, column) for r in range(row + 1, row + v)}
                return cells
        # Degenerate fallback; real BENT specs always fit.
        return self._straight_path(rng, rows, columns, target)

    def _grow_tree(self, rng, rows, columns, target, acyclic=False):
        # Grow a connected region by expanding a random frontier. For a tree,
        # a new cell may touch exactly one open neighbor, which prevents cycles.
        start = (rng.randrange(rows), rng.randrange(columns))
        opened = {start}
        frontier = [neighbor for neighbor in self._neighbors(*start)
                    if 0 <= neighbor[0] < rows and 0 <= neighbor[1] < columns]
        while len(opened) < target and frontier:
            index = rng.randrange(len(frontier))
            cell = frontier.pop(index)
            connections = [neighbor for neighbor in self._neighbors(*cell)
                           if neighbor in opened]
            if acyclic and len(connections) != 1:
                continue
            if not connections:
                continue
            opened.add(cell)
            for neighbor in self._neighbors(*cell):
                if (0 <= neighbor[0] < rows and 0 <= neighbor[1] < columns
                        and neighbor not in opened and neighbor not in frontier):
                    frontier.append(neighbor)
        return opened

    @staticmethod
    def _has_branch(opened):
        for row, column in opened:
            degree = sum((neighbor in opened) for neighbor in ((row - 1, column), (row + 1, column), (row, column - 1), (row, column + 1)))
            if degree >= 3:
                return True
        return False

    def generate_terrain(self, specification: TerrainGenerationSpec, seed: int) -> Terrain:
        self._last_seed = seed
        self._last_spec = specification
        self._generated += 1
        rng = random.Random(seed)
        rows, columns = specification.rows, specification.columns
        low, high = specification.min_open_tiles, specification.max_open_tiles
        max_cells = rows * columns
        target = min(high, max_cells) if low <= high else min(low, max_cells)
        if low != high:
            target = rng.randint(low, min(high, max_cells))
        topology = specification.topology
        if topology is TerrainTopology.STRAIGHT_PATH:
            opened = self._straight_path(rng, rows, columns, target)
        elif topology is TerrainTopology.BENT_PATH:
            opened = self._bent_path(rng, rows, columns, target)
        elif topology is TerrainTopology.BRANCHING_TREE:
            # Grow candidate trees until one hits the target open count and
            # contains a degree-3 branch. Each attempt advances the same seeded
            # rng, so the result stays deterministic.
            attempts = max(specification.max_attempts * 4, 8)
            opened = self._grow_tree(rng, rows, columns, target, acyclic=True)
            for _ in range(attempts):
                if len(opened) == target and self._has_branch(opened):
                    break
                opened = self._grow_tree(rng, rows, columns, target, acyclic=True)
        else:
            opened = self._grow_tree(rng, rows, columns, target)
        grid = [['#'] * columns for _ in range(rows)]
        for row, column in opened:
            grid[row][column] = '.'
        return Terrain(terrain_rows=tuple(''.join(entry) for entry in grid))

Determinism lives at line 86: rng = random.Random(seed) is created fresh, inside the method. Nothing seeded is stored on the instance — that's why two separate generator objects give identical maps for the same inputs. The _last_* fields (lines 12–13) are only diagnostics; they never drive randomness.

Target selection (lines 90–92): the open-tile count is chosen from the spec's bounds with the seeded rng. If min == max, it's fixed; otherwise it's rolled inside the range.

Shape recipes: _straight_path (line 20) draws one line on the axis that fits. _bent_path (line 30) tries an L where horizontal + vertical − 1 == target, retrying up to 200 times. _grow_tree (line 51) grows from a random seed; with acyclic=True a new cell must touch exactly one open neighbor (line 63) — that rule is what prevents loops.

Tree branch requirement (lines 98–107): a tree isn't accepted until it reaches the target size and has a degree-3 branch (_has_branch, line 74). Since every retry advances the same seeded rng, the whole thing stays deterministic.

import random

from src.api import (
    ArtifactDefinition, CharacterDefinition, EnemyDefinition, LevelDefinition,
    LevelSpecification, Position, TerrainGeneratorContract, TerrainTopology,
)


class LevelGenerator:
    """Use the supplied TerrainGeneratorContract; do not instantiate a replacement."""

    def __init__(self, terrain_generator: TerrainGeneratorContract) -> None:
        self._generator = terrain_generator

    def _open_tiles(self, terrain):
        return [
            (row, column)
            for row in range(terrain.rows)
            for column in range(terrain.columns)
            if terrain.is_traversable(Position(row, column))
        ]

    def _degree_one(self, terrain, open_tiles):
        result = []
        for row, column in open_tiles:
            degree = sum(
                (row + dr, column + dc) in open_tiles
                for dr, dc in ((0, 1), (0, -1), (1, 0), (-1, 0))
            )
            if degree == 1:
                result.append((row, column))
        return result

    def _pick_endpoints(self, rng, specification, terrain, open_tiles):
        topology = specification.terrain_spec.topology
        if topology in (TerrainTopology.STRAIGHT_PATH, TerrainTopology.BENT_PATH):
            ends = self._degree_one(terrain, open_tiles)
            if len(ends) >= 2:
                return Position(*ends[0]), Position(*ends[1])
        # General / tree: start at the top-left open tile, then choose an exit
        # whose route distance fits the requested bounds.
        start = Position(*open_tiles[0])
        low, high = specification.min_route_moves, specification.max_route_moves
        for row, column in open_tiles[1:]:
            candidate = Position(row, column)
            if low <= candidate.manhattan_distance(start) <= high:
                return start, candidate
        return start, Position(*open_tiles[-1])

    def _place_entities(self, rng, specification, open_tiles, start, exit_pos):
        start_pair = (start.row, start.column)
        exit_pair = (exit_pos.row, exit_pos.column)
        artifact_blocked = set()
        enemy_blocked = {start_pair}  # enemies never occupy the start
        if not specification.allow_entities_on_endpoints:
            artifact_blocked |= {start_pair, exit_pair}
            enemy_blocked.add(exit_pair)
        artifact_pool = [tile for tile in open_tiles if tile not in artifact_blocked]
        enemy_pool = [tile for tile in open_tiles if tile not in enemy_blocked]
        rng.shuffle(artifact_pool)
        rng.shuffle(enemy_pool)
        used = set()
        artifacts = []
        for index in range(specification.artifact_count):
            if not artifact_pool:
                break
            tile = artifact_pool.pop()
            if not specification.allow_entity_overlap:
                while tile in used and artifact_pool:
                    tile = artifact_pool.pop()
                if tile in used:
                    break
            used.add(tile)
            value = rng.randint(specification.artifact_value_min, specification.artifact_value_max)
            artifacts.append(ArtifactDefinition(f"ART-{index + 1}", Position(*tile), value))
        enemies = []
        for index in range(specification.enemy_count):
            if not enemy_pool:
                break
            tile = enemy_pool.pop()
            if not specification.allow_entity_overlap:
                while tile in used and enemy_pool:
                    tile = enemy_pool.pop()
                if tile in used:
                    break
            used.add(tile)
            penalty = rng.randint(specification.enemy_penalty_min, specification.enemy_penalty_max)
            enemies.append(EnemyDefinition(f"ENM-{index + 1}", Position(*tile), penalty))
        return tuple(artifacts), tuple(enemies)

    def generate_level(self, specification: LevelSpecification, seed: int) -> LevelDefinition:
        rng = random.Random(seed)
        terrain = self._generator.generate_terrain(specification.terrain_spec, seed)
        open_tiles = self._open_tiles(terrain)
        start, exit_pos = self._pick_endpoints(rng, specification, terrain, open_tiles)
        artifacts, enemies = self._place_entities(rng, specification, open_tiles, start, exit_pos)
        return LevelDefinition(
            level_id=specification.level_id,
            profile_id=specification.profile_id,
            seed=seed,
            terrain=terrain,
            start=start,
            exit=exit_pos,
            character=CharacterDefinition(specification.agent_id),
            artifacts=artifacts,
            enemies=enemies,
        )

"""TODO: select one public action from each immutable world observation."""
import heapq

from src.api import Position, WorldAction, WorldActionType, WorldSnapshot


class AgentController:
    """A new controller is constructed for each run; arrival still needs EXIT."""

    def __init__(self) -> None:
        self.turn_count = 0

    @staticmethod
    def _patrol_position(patrol, turn):
        # The patrol moves once per accepted action, so its phase at `turn` is
        # purely a function of the schedule and the number of accepted actions.
        phase = (patrol.initial_phase + turn) % len(patrol.positions)
        return patrol.positions[phase]

    def _patrol_cells(self, state, turn):
        return [self._patrol_position(patrol, turn) for patrol in state.level.patrols]

    def _static_enemies(self, state):
        # Enemies that own a patrol are dynamic and cannot be engaged; only the
        # remaining static, undefeated enemies are clearable blockers.
        patrol_ids = {patrol.enemy_id for patrol in state.level.patrols}
        return [
            enemy for enemy in state.level.enemies
            if enemy.enemy_id not in state.defeated_enemy_ids
            and enemy.enemy_id not in patrol_ids
        ]

    def _plan(self, state):
        """Lowest-cost path over (position, turn, defeated) states.

        Every accepted action advances the patrol clock by one turn, so routes
        are planned against the *future* positions of each patrol, not just the
        current snapshot. Static enemies are entered by ENGAGEing them first
        (which costs one action plus the encounter penalty); patrols are never
        engaged — only timed around. Total cost is actions plus encounter
        penalties, matching the workbench's scoring. Returns a list of
        (action_type, target_id) steps, or None if the exit is unreachable.
        """
        limit = state.deadline_turn if state.deadline_turn is not None else state.max_turns
        start_defeated = frozenset(state.defeated_enemy_ids)
        static_enemies = self._static_enemies(state)
        start = (state.agent_position, state.turn, start_defeated)
        dist = {start: 0}
        previous = {start: None}
        pending = [(0, start)]
        goal = None
        moves = ((0, 1, WorldActionType.MOVE_EAST), (0, -1, WorldActionType.MOVE_WEST),
                 (1, 0, WorldActionType.MOVE_SOUTH), (-1, 0, WorldActionType.MOVE_NORTH))
        while pending:
            cost, current = heapq.heappop(pending)
            if current not in dist or cost > dist[current]:
                continue
            position, turn, defeated = current
            if position == state.level.exit:
                goal = current
                break
            if turn + 1 >= limit:
                continue
            patrol_now = self._patrol_cells(state, turn)
            patrol_next = self._patrol_cells(state, turn + 1)
            for step_row, step_column, action_type in moves:
                step = Position(position.row + step_row, position.column + step_column)
                if not state.level.terrain.is_traversable(step):
                    continue
                # The next tile must be clear now and clear right after the move
                # advances the patrol clock (otherwise the agent collides).
                if step in patrol_now or step in patrol_next:
                    continue
                # A static enemy cell is entered only after ENGAGEing it, so it
                # is not a plain-move destination.
                if any(enemy.enemy_id not in defeated and enemy.position == step
                       for enemy in static_enemies):
                    continue
                node = (step, turn + 1, defeated)
                if cost + 1 < dist.get(node, float("inf")):
                    dist[node] = cost + 1
                    previous[node] = (current, action_type, None)
                    heapq.heappush(pending, (cost + 1, node))
            # Staying put for one accepted action (ENGAGE / WAIT) is only safe if
            # no patrol is here now and none arrives afterwards.
            if position not in patrol_now and position not in patrol_next:
                for enemy in static_enemies:
                    if (enemy.enemy_id not in defeated
                            and abs(enemy.position.row - position.row)
                            + abs(enemy.position.column - position.column) == 1):
                        node = (position, turn + 1, defeated | {enemy.enemy_id})
                        step_cost = cost + 1 + enemy.encounter_penalty
                        if step_cost < dist.get(node, float("inf")):
                            dist[node] = step_cost
                            previous[node] = (current, WorldActionType.ENGAGE, enemy.enemy_id)
                            heapq.heappush(pending, (step_cost, node))
                if WorldActionType.WAIT in state.allowed_actions:
                    node = (position, turn + 1, defeated)
                    if cost + 1 < dist.get(node, float("inf")):
                        dist[node] = cost + 1
                        previous[node] = (current, WorldActionType.WAIT, None)
                        heapq.heappush(pending, (cost + 1, node))
        if goal is None:
            return None
        steps = []
        current = goal
        while current != start:
            current, action_type, target = previous[current]
            steps.append((action_type, target))
        steps.reverse()
        return steps

    def choose_action(self, state, agent_id) -> WorldAction:
        self.turn_count += 1
        position = state.agent_position
        # If we are standing on the exit tile, leave.
        if position == state.level.exit:
            return WorldAction(action_type=WorldActionType.EXIT)
        # Collect an uncollected artifact on this tile, as long as no patrol is
        # about to arrive on this cell after the collection advances the clock.
        for artifact in state.level.artifacts:
            if (artifact.artifact_id not in state.collected_artifact_ids
                    and artifact.position == position
                    and position not in self._patrol_cells(state, state.turn + 1)):
                return WorldAction(action_type=WorldActionType.COLLECT, target_id=artifact.artifact_id)
        plan = self._plan(state)
        if plan:
            action_type, target_id = plan[0]
            return WorldAction(action_type=action_type, target_id=target_id)
        return WorldAction.wait()

Public entry — choose_action (line 113): this is called once per turn with a fresh snapshot, and must return exactly one action. Order matters: EXIT if on the exit (line 117), then COLLECT if there's an uncollected artifact under you and no patrol is about to arrive (lines 121–125), then follow the plan (line 126), else WAIT (line 130).

The whole algorithm is _plan (line 33): a Dijkstra search over states, where a state is (position, turn, defeated) — not just position. That's the key trick: because patrols move with the clock, two visits to the same tile at different turns were not equivalent, so the state must include time.

Cost model (lines 55–102): a move costs 1 action; an ENGAGE costs 1 action + the enemy's penalty (line 92); WAIT costs 1 action. That total is exactly the workbench's C = T + P, so the cheapest route found is the highest-scoring one.

Patrol safety (lines 64–65, 72): a move is rejected if the destination is a patrol cell now (line 72's first check) or after the clock advances (second check) — that second check is the collision rule. Same idea for staying put (line 86): ENGAGE/WAIT are only allowed if no patrol is here now or about to arrive.

Patrol phase (line 17): phase = (initial_phase + turn) % len(positions) is the exact schedule formula. A patrol at turn t is at positions[phase]. It moves once per accepted action, which is why turn — the number of accepted actions — indexes it.

No-combat guarantee (lines 23–31, 86–96): _static_enemies excludes enemies that own a patrol (line 27). ENGAGE is only ever offered for static, undefeated, adjacent enemies (lines 87–90). Patrols are never engaged — only timed around.

Deep dive B · the algorithm

Why the planner searches

The controller never "walks toward the exit." Instead it runs a lowest-cost search over states and follows the cheapest route. Here's the classic decision, with the two candidate routes on the same map.

The tradeoff

Direct route (red): engage the enemy, then walk through. Cost = 1 action for ENGAGE + 5 moves + 1 EXIT = 7 actions, plus penalty 6 ⇒ C = 13.

Detour (green): loop around the wall. Cost = 5 moves + 1 EXIT = 6 actions, no penalty ⇒ C = 6.

The planner picks green — more tiles, less cost. That's the whole reason it optimizes C = T + P, not distance.

Why not just greedy?

A greedy "move toward the exit" controller would head straight into the wall or the enemy. On a map where the first step away from the exit is a wall, it has no legal move and — because WAIT is allowed — it sits forever. That's the WAIT-lock. Searching fixes it.

The collision rule, restated

Patrols advance once per accepted action. So after you move, the clock ticks and the patrol advances. Your destination must be clear now and clear right after the tick — the controller checks both (patrol_now and patrol_next).

Inside the referee

The referee isn't one check — it's a chain. Each group asserts something specific, and any one failing fails the whole session.

Validator groupWhat it asserts
SpecThe spec is well-formed: ranges sane, topology valid, ids valid.
RequestTerrain request → generation respects the spec contract.
TerrainCorrect rows/columns, open-tile bounds, topology shape, connectedness.
LevelEndpoints on traversable tiles, entities legal, no illegal overlaps/endpoints, values in range.
DeterminismSame spec + seed on fresh instances produce byte-identical results (A/A, B/A).
InventoryThe controller's actions follow rules: valid target ids, no illegal collections/engages.

◇Self-check quiz

Pick an answer, then reveal the explanation. These are the exact concepts you're most likely to be asked about.

1 · Why does the controller plan a route instead of always walking toward the exit?
Correct: the grid isn't a straight line. Only search-based planning guarantees you actually reach the exit.
2 · Walking onto an artifact's tile automatically collects it. True or false?
False. Collection is an explicit action on that tile. The object itself never awards points.
3 · You can clear a patrol by engaging it.
Correct. Patrols are immune to ENGAGE. The only way past is predicting their schedule.
4 · After you take an accepted action, what happens to the patrol clock?
Correct. Every accepted action advances the patrol clock one step. WAIT is never "free."
5 · A level is "solvable" because…
Correct. Connectivity plus legal placement plus referee validation is the chain that guarantees solvability.

◇Glossary

seed

An integer that starts the random generator. Same seed ⇒ same world.

terrain

The floor/wall grid; answers "is this cell walkable?"

topology

The shape recipe: straight, bent, branching tree, or general.

snapshot

A read-only, immutable view of the whole world on one turn.

agent

The explorer — controlled by your controller.py.

artifact

A reward with a value, sitting on a tile.

enemy

A static blocker cleared by ENGAGE, with a penalty.

patrol

A moving guard on a repeating schedule; can't be engaged.

phase

A patrol's current position in its schedule (starts at initial_phase).

ENGAGE

Clear an adjacent static enemy; pay its penalty; don't move.

collision

Ending a move on a cell a patrol just occupied → loss.

determinism

Same inputs produce same outputs, across fresh instances.

excess cost (E)

How much you spent beyond the reference baseline L.

deadline (D)

Turn count patrol worlds must finish within.

referee

The automated grader/validator chain that scores submissions.
